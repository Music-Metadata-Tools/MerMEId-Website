# Repository Configuration

Each **data repository** contains a configuration file at `configuration/config.json`. This file should always be present and correctly configured. If it is missing or invalid, the editor shows the warning *"Using default configuration"* and falls back to default values.

---

## Location

```
my-catalogue/
└── configuration/
    └── config.json   ← this file
```

The editor reads this path relative to the repository root when a repository is loaded. The path cannot be changed.

---

## Example

```json
{
  "datasetBaseUrl": "https://yourname.github.io/my-catalogue/datasets/",
  "projectDomain": "urn:uuid:"
}
```

---

## Fields

### `datasetBaseUrl`

The base URL where published dataset index files were hosted in earlier versions (a GitHub Pages or GitLab Pages URL).

**Current behaviour:** the value is kept for compatibility. The URL itself is currently **not** used to fetch anything. Keep the value with the template url.

**Example:**
```json
"datasetBaseUrl": "https://yourname.github.io/my-catalogue/datasets/"
```

#### What Are Datasets?

Datasets (index files) are aggregated RDF/Turtle files built from your repository's data, stored in the `indexes/` folder of the repository. They are **generated by a CI/CD pipeline** after each push to `main` using SPARQL CONSTRUCT queries, and the editor updates them itself whenever you save, delete or synchronise entities. Each dataset corresponds to an entity type:

- `persons.ttl` — all persons (indexed by full name)
- `works.ttl` — all works (indexed by title)
- `institutions.ttl` — all institutions (indexed by name and abbreviation)
- `places.ttl` — all places (indexed by name)
- `venues.ttl` — all venues (indexed by name and location)
- `manifestations.ttl`, `expressions.ttl`, `items.ttl`, `bibliography.ttl`, `letters.ttl`, `dataCollections.ttl`, etc.

For a complete list and how each dataset is built, see [Datasets Generation](datasets.md).

#### How Datasets Are Used

The index files are used in three ways:

1. **Entity search** — the `adwlm-entity-search` component loads all index files from `indexes/` into its Oxigraph SPARQL store. When you search for "Bach" in the editor, it queries these indexes rather than scanning individual entity files.

2. **Cross-reference dropdowns in forms** — linked entity fields (e.g., "Contributor", "Birth Place") list the entities of the index files. When a form is opened, the editor appends all files from `indexes/` to the SHACL shape, so `shacl-form` can offer every entity of the requested class (e.g. `melod:PlaceEntity`).

3. **Graph view** — the relations between entities (`skos:related`) are read from the index files.

!!! note
    The index files reflect the files in your local copy of the repository. The editor updates them on save, and the CI/CD pipeline rebuilds them after every push to `main`. Changes of other users become visible after synchronising.

### `projectDomain`

The IRI prefix used when generating identifiers for new entities.

**Default value:** `"urn:uuid:"` — produces opaque identifiers like `urn:uuid:persons/2847362910`

**Alternative:** an HTTPS namespace — produces dereferenceable URIs like `https://example.org/persons/2847362910`

```json
"projectDomain": "https://example.org/"
```

The `projectDomain` is also used for the fixed IRIs of the data catalog and the default data collections (`<projectDomain>dataCatalogs/catalog`, `<projectDomain>dataCollections/works`, `<projectDomain>dataCollections/manifestations`).

See [Entity IRIs](../data_model/iris.md) for full details on IRI generation and the implications of changing this value.

!!! warning
    Changing `projectDomain` after entities have been created does **not** retroactively update existing entity IRIs. Existing entities keep their original IRIs. New entities will use the new prefix, resulting in a mixed-prefix dataset. Decide on your IRI scheme before creating any entities.

---

### `IDprefix`

A prefix for chosen entity types, which is inserted in front of the identifier number. This configuration is optional.

**Default value:** `"1477695404"` — produces opaque identifiers like `urn:uuid:works/1477695404`

**Alternative:** an IRI with a prefix to distinguish entity types with a character — for example `w1477695404` for works, full IRI: `urn:uuid:works/w1477695404`. This is done by adding the folder name with the chosen prefix.

Only the entities of the folders named in the config.json will get a prefix.

```json
"IDprefix": {
    "works": "w",
    "persons": "p"
  }
```

!!! warning
    Changing `IDprefix` after entities have been created does **not** retroactively update existing entity IRIs. Existing entities keep their original IRIs. New entities will use the new prefix, resulting in a mixed-prefix dataset. Decide on your IRI scheme before creating any entities.

## Typical Setup (GitHub)

If you created your repository from the [MerMEId MeLODy Template](https://github.com/Music-Metadata-Tools/MerMEId-MeLODy-Template) on GitHub, the typical `config.json` looks like:

```json
{
  "datasetBaseUrl": "https://music-metadata-tools.github.io/MerMEId-MeLODy-Template/datasets/",
  "projectDomain": "urn:uuid:"
}
```

Keep the `config.json` shipped with the template; usually only `projectDomain` (and optionally `IDprefix`) needs a decision. No GitHub Pages setup is required. Make sure GitHub Actions may push to `main`, so the **Build and Push Indexes** workflow can commit the `indexes/` folder.

## Other Repository Files

Besides `config.json`, every data repository contains files that are managed by the editor:

- `dataCatalogs/catalog.ttl` — the data catalog of the repository (`melod:DataCatalog`), edited via the **Catalog metadata** button. Fields: name, contributors with roles (data manager, data contributor, editor, contributor, publisher), application ("MerMEId MeLODy"), description.
- `dataCollections/` — data collections (e.g. a work catalogue or a source catalogue) belonging to the data catalog. Fields: name, data catalog, type ("work catalog" / "source catalog"), restrictions of use, status (draft, candidate, approved, published), responsible. The default collections `works.ttl` ("All works") and `manifestations.ttl` ("All manifestations") are created automatically; new works and manifestations are added to them.
- `indexes/` — generated index files, see [Datasets Generation](datasets.md). Do not edit them by hand.

The catalog files are created automatically when a repository is selected for the first time, if they are missing.

The username and personal access token are **not** part of `config.json` — they are stored per user in the browser and can be changed in the **Repository settings** dialog.
